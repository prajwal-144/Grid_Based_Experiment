------------------------------------------------------------------------------
  INTERPRETATION
  The pipeline composes backward then forward. It is self-consistent
  ONLY if the two carry OPPOSITE signs (one +alpha, one -alpha), so the
  round trip is the identity. Same sign on both means the deflection is
  applied twice in the same direction.
  Note raw_matrices_old/create_backward_grid.ipynb calls backward_lensing
  (theta + alpha) while create_backward_grid.ipynb calls forward_lensing
  (theta - alpha). Both forward notebooks call forward_lensing. If the
  measurement above shows the same sign for backward and forward in a
  directory, that directory's backward matrix has the flipped convention.

[4] THE MAGNIFICATION REGULARIZER IS A DONUT PRIOR
==============================================================================
train_all_wo_mapping.magnification_regularizer computes
    (weight * laplacian(source)^2).sum() / weight.sum(),  weight = (1-info)^2
info comes from |mu| = |1/(1 - theta_E/r)| compressed to [0,1].
For an SIS, |mu| -> 0 at r=0, peaks at r=theta_E, -> 1 far out. So info
is an ANNULUS, and (1-info)^2 is LARGE at the source centre and ZERO on
the ring. The penalty therefore forbids curvature exactly where a
compact source lives, and permits it exactly on a ring.

  --- resolution 0.168 arcsec/px   critical radius 4.46 px ---
      info(source) range      : 0.000 .. 0.960
      weight at r=0           : 1.000
      info peaks at r         : 11.38 px
      weight there            : 0.103
      centre/ring weight ratio: 9.7x
      => curvature at the centre is penalised 10x harder than on the ring

  --- resolution 0.101 arcsec/px   critical radius 7.43 px ---
      info(source) range      : 0.000 .. 0.979
      weight at r=0           : 1.000
      info peaks at r         : 14.35 px
      weight there            : 0.028
      centre/ring weight ratio: 35.2x
      => curvature at the centre is penalised 35x harder than on the ring

  This term is scaled by --mu-weight. Going 0.001 -> 0.01 multiplies
  the donut prior by ten. Its share of the total loss stays small, but
  the image-fidelity term barely constrains the source interior (that
  is the null space of a fixed-SIS inversion), so a small term can still
  dictate what the source looks like there.
  history.json corroborates this: in mag_full_latest_101 the mu term
  falls 0.775 -> 0.11 (7x) once the ramp engages, while the source loss
  RISES 0.033 -> 0.037.

[5] DID THE 0.168 -> 0.101 SWITCH CHANGE THE PSF?
==============================================================================
psf.resample_kernel_to_pixscale uses
    scale_factor = source_pixscale_arcsec / target_pixscale_arcsec
    0.168 / 0.084 = 2.000000
    0.101 / 0.0505 = 2.000000

  Both runs pass --psf-source-pixscale-arcsec equal to --resolution, and
  target_resolution = resolution / 2. The ratio is 2.0 in both cases, so
  the resampled kernel is IDENTICAL. Switching to Euclid pixel scales
  did not change the PSF by a single pixel.

  Separately: the FITS file is an HSC PDR2 PSF, natively 0.168 arcsec/px.
  Declaring --psf-source-pixscale-arcsec 0.101 asserts a pixel scale the
  stamp does not have. That is wrong on its own terms, but because only
  the ratio is used it happens to cancel here. Fix it anyway, after the
  geometry: a PSF cannot move flux from the centre out to an annulus, so
  it is not what makes the donut.
